# Resolution — `metro-resolver` + `DependencyGraph`

## The split

| Layer | File | Role |
|---|---|---|
| Pure algorithm | `packages/metro-resolver/src/resolve.js` | `(ResolutionContext, specifier, platform) => Resolution`. **No I/O, no state, no caching.** |
| Capability binding | `packages/metro/src/node-haste/DependencyGraph/createModuleResolver.js` | Binds the context's capabilities to `TreeFS`, `PackageCache`, `HastePlugin`, config |
| Per-resolution adapter | `packages/metro/src/node-haste/DependencyGraph/ModuleResolution.js` | `ModuleResolver.resolveDependency`: assembles the context per call (adding per-request values), coerces `Resolution` → `BundlerResolution`, formats errors |
| Orchestration + caching | `packages/metro/src/node-haste/DependencyGraph.js` | Memoizes resolutions, owns invalidation, translates errors |

This split is the whole design. `metro-resolver` is a pure function so it can be unit-tested exhaustively against in-memory fixtures, memoized safely by the caller, wrapped by user `resolveRequest`, and reasoned about. **Never add I/O, a cache, or config access to `metro-resolver`** — add a member to `ResolutionContext` (checklist at the end). The one memo inside proves the rule: `PackageExportsResolve.js` keys a `WeakMap` of normalized `exports` on the parsed object, so a manifest change can't leave it stale.

`ModuleResolver.resolveDependency` passes `Resolver.resolve` a context literal on every `_resolutionCache` miss, then `_getFileResolvedModule` maps the result: `empty` → `emptyModulePath` (default `metro:runtime/modules/empty-module`) resolved from a fake `<projectRoot>/_` with `allowHaste: false`, memoized as `_cachedEmptyModule` for the resolver's lifetime — an error if that resolution is itself `empty`, as when a custom `resolveRequest` doesn't delegate it; `assetFiles` → the lexicographically lowest path (a `FIXME` notes the rest are dropped); `virtualModule` → a `virtual:`-namespaced module with its source attached ("Virtual resolutions" below).

## What resolution can see

Only the file map: `config.watchFolders` (`packages/metro/src/node-haste/DependencyGraph/createFileMap.js`) with `projectRoot` prepended by `loadConfig`, plus any roots added with `FileMap.addRoot` — on main, Metro's own `metro-runtime` and its `@babel/runtime`, added by `DependencyGraph._addMetroRuntimeRoots` before ready so that `metro:` targets resolve even outside every configured root (`references/file-map.md`, "Roots and `addRoot`"). Anything outside is `{exists: false}` however real on disk — a missing node "could indicate an unwatched path, or a directory containing no watched files". The one way to reach a module with no file is a `VirtualResolution`, whose source the resolver supplies. URL ↔ path mapping (`packages/metro/src/lib/RootUrlMap.js`, `DependencyGraph.getDynamicRoots()`) belongs to the server side — `Server`, `HmrServer`, and `Transformer` for asset URLs — applied before and after resolution, never inside it.

## Why resolution is fast

**Every existence, type, realpath and package-scope question in resolution is a `TreeFS` map walk. Zero syscalls.** Two bounded exceptions: `PackageCache` reads each `package.json` with `readFileSync` on first use, and `UnableToResolveError` reads the origin file for its code frame (error path only; a virtual origin is normally missing on disk, so it gets no frame). The `metro:` scheme locates Metro's runtime packages with `require.resolve` (`lib/metroRuntime.js`, `lib/metroBabelRuntime.js`), memoized, but `_addMetroRuntimeRoots` makes both calls at startup, so resolution normally hits the memo.

The rest is constant factors:

- `fileSystemLookup(path)` returns `{exists, type, realPath}` in one traversal — existence, type and realpath together, because the traversal already resolved symlinks on the way down. It is the context's only existence check (`resolvePackageEntryPoint` uses it for both the directory and its `package.json`). Default resolution returns real paths.
- `resolveFromNodeModulesPath` short-circuits an entire `node_modules` level with **one** directory lookup, justified by an explicit invariant in a comment: the module can only exist if `node_modules[/firstPart]` is a real directory, and redirections can't succeed because we never look past a `node_modules` segment for the closest `package.json`. That's the pattern — **find an invariant that lets you skip a whole branch, and write the invariant down.**
- **Package scope once per directory.** `resolveFile` calls `getCandidatePackageScope`, which asks `getPackageForModule` about `<dir>/package.json` (which needn't exist) and shares the answer with every extension candidate through the `SourceFileContext`. Each candidate is looked up first: one that is a directory is redirected through its own scope ("A directory may be a package root, i.e. its own package scope"), at the cost of one more `getPackageForModule` call; any other gets its `browser`-style redirection with `redirectPackageSubpath` against the shared scope, and a redirected candidate costs a second `fileSystemLookup`. `metro-resolver/src/__tests__/package-scope-test.js` pins the sequence of `getPackageForModule` calls for each specifier shape, so a change in lookups per resolution has to be deliberate.
- Failed path candidates are recorded as the probe loop misses (`candidateExts.push`), so a path error needs no second pass — but misses before the hit push too, and `resolveFile` spreads the whole context into a `SourceFileContext` per call.

## Algorithm order (`resolve.js`)

1. `context.resolveRequest` (custom resolver) — takes precedence over everything, receives a frozen context whose `resolveRequest` is the default `resolve` so it can delegate. It runs before scheme dispatch, so it must delegate `metro:` specifiers it doesn't handle — by default these include `emptyModulePath`, `asyncRequireModulePath` and the module system (step 4).
2. **Relative / absolute** specifier → `resolveModulePath`.
3. **Subpath import** (`#foo`) → `imports` of the origin's closest package; not gated by `unstable_enablePackageExports`, and no `browser` redirection follows. No `package.json` or no `imports` throws; a failed match (including a target naming a package, which Metro doesn't support) or an invalid configuration logs a warning and falls through to steps 5–10, which treat `#foo` as a bare specifier.
4. **URI scheme** (`foo:bar`, if `URL.canParse`) → `schemeResolvers[scheme]`, keyed lowercase. Otherwise remember a `schemeError` and fall through (compatibility with scheme-like Haste names), throwing it only if everything else fails. Metro registers its own `metro:` resolver (`packages/metro/src/lib/metroSchemeResolver.js`) beneath config's. `metro:babel-runtime[/subpath]` and `metro:runtime[/subpath]` re-root the origin at the `package.json` of, respectively, metro-runtime's `@babel/runtime` and Metro's own `metro-runtime`, and delegate as a package self-reference; `metro:runtime` forces `unstable_enablePackageExports: true`, since its subpaths exist only in `exports`. They let modules Metro injects resolve from any importer, whatever the `node_modules` layout, and the defaults use them: `transformer.asyncRequireModulePath` is `metro:runtime/modules/asyncRequire`, `resolver.emptyModulePath` is `metro:runtime/modules/empty-module`, the module system is `metro:runtime/polyfills/require` (`metro-config`'s `defaults.moduleSystem`, resolved by `getPrependedScripts` from `<projectRoot>/.`), and with `transformer.enableBabelRuntime` (the default) the transform worker passes `babelRuntimeModuleName: 'metro:babel-runtime'` to Babel presets via caller data. These resolutions don't depend on the origin, but `_resolutionCache` still stores one per origin directory. `metro:inline` returns a virtual resolution ("Virtual resolutions" below).
5. **`browser`-field redirection** from the origin's closest package (`mainFields`). `false` ⇒ `{type: 'empty'}`; a relative target resolves against that package's root; an absolute one throws `InvalidPackageConfigurationError`; a bare one replaces the specifier.
6. **Haste**, only if `allowHaste` (false only for `emptyModulePath`): a Haste module (single-segment specifiers only), then a Haste package (whose `exports` come from its own root under `unstable_resolveExportsFromPackageRoot`). A matched Haste package lacking the subpath throws.
7. **`PACKAGE_SELF_RESOLVE`** — with `unstable_enablePackageExports`, origin inside a package whose `name` matches and which has `exports`; under `unstable_applyBrowserSpecAfterExports` the resolved file is then redirected as in step 8. A failed `exports` match logs a warning and falls back — "a departure from the spec, but retained for backwards compatibility".
8. **Hierarchical `node_modules` walk** up from `dirname(originModulePath)`, then `nodeModulesPaths` (`$NODE_PATH`-like), skipping already-visited paths. With `disableHierarchicalLookup`, only `nodeModulesPaths`. Each level is gated by one directory lookup, then `resolveModuleFromTargetPath` resolves `<node_modules>/<specifier>` as a package (below); a failure moves on to the next level.
9. **`extraNodeModules`** remapping, through the same `resolveModuleFromTargetPath`, except that a mapped directory with no `package.json` uses the closest package's `exports`.
10. Throw `schemeError` if set, else `FailedToResolveNameError`.

Within a directory (`resolveSourceFile`), the order is: bare path, then for each `sourceExts` entry in order — `.<platform><ext>`, then `.native<ext>` (if `preferNativePlatform`), then `<ext>`. Note `foo.ios` (platform without extension) is **not** supported, "for historical reasons".

A name matching `assetExts` (any dot-suffix, so multi-part extensions work) takes the asset branch: `context.resolveAsset` does one `fileSystemLookup` for the unscaled path and one per `assetResolutions` variant, and **only regular files count** — "A directory such as `node_modules/lodash.zip` is not an asset, and must fall through to directory (package) resolution." Asset-ness is decided by name alone and `zip` is a default asset extension, so the type check is all that separates the two.

**Package resolution** (`resolveModuleFromTargetPath`, then `resolvePackage`) takes a candidate such as `<node_modules>/<specifier>` through three steps, governed by two options that both default to `true`:

1. **Pick the package whose `exports` apply.** Under `unstable_resolveExportsFromPackageRoot`, that is the `package.json` at the root of the package the bare specifier names (`getRootPackageForExports`), as in Node.js PACKAGE_RESOLVE: its subpath is the literal text after the name, so `pkg/./sub` matches nothing; a pattern match containing a `.`, `..` or `node_modules` segment is unexported; and a `node_modules` package with no `package.json` at its root has no `exports`. Without it, the package closest to the candidate.
2. **`browser` redirection, before or after `exports`.** Under `unstable_applyBrowserSpecAfterExports`, when that package has `exports`, the requested subpath goes to `exports` unredirected, and a `browser`-style map then applies to the source file `exports` resolved to (assets excepted), read from that file's closest package — `false` ⇒ `empty`, and a redirection that doesn't resolve warns and keeps the `exports` file. Otherwise the candidate is redirected first, through its closest package (`false` ⇒ `empty`), and a redirected candidate takes its `exports` from the root package if it stays inside the root's directory and outside a nested `node_modules`, else from its own closest package (`getPackageForRedirectedPath`).
3. **Match `exports`** when `unstable_enablePackageExports` (the default) is set and the package has one. `PackagePathNotExportedError` or `InvalidPackageConfigurationError` logs a warning and falls back to file-based resolution of the same path (`resolveModulePath`: its own `browser` redirection, then the subpath as a file, then as a directory, whose entry point `mainFields` pick).

`imports`, the origin's `browser` map (step 5) and self-reference always use the closest package. `exports` and `imports` share `packages/metro-resolver/src/utils/matchSubpathFromExportsLike.js`, which picks the exact key or the most specific pattern first and then reduces only that value (`utils/reduceConditionalExport.js`), validating targets as it goes. Conditions are `default`, `import` or `require` (from `isESMImport`), `unstable_conditionNames` and `unstable_conditionsByPlatform[platform]`. They match in the package's key order, recursing into nested condition objects: a nested object with no matching condition falls through to the parent's next matching key, while an explicit `null` excludes the entry. An array is an ordered fallback list at any depth — the first element yielding a valid target wins, an invalid element is skipped, and a missing file at the chosen target is not retried against later elements. "An exact key takes precedence even when its target is null", so `"./internal": null`, or an exact key with no matching condition, is unexported rather than matching `"./*"` (step 2 of `PACKAGE_IMPORTS_EXPORTS_RESOLVE`). An `exports` field that is neither a string, an array nor an object is a configuration error, so it warns and falls back. See `docs/PackageExports.md`.

## Errors are data

`FileCandidates` describes *what was tried* (`{type: 'sourceFile', filePathPrefix, candidateExts}` or `{type: 'asset', name}`), and `errors/formatFileCandidates.js` renders it. **Preserve structured failures** — `schemeResolvers` error handling explicitly re-throws resolution errors rather than wrapping them, so the candidate list survives. A bare-name failure (`FailedToResolveNameError`) is coarser: it carries only the `node_modules` directories considered (plus any `extraNodeModules` target), recomputed after the walk, and the file candidates inside each package are dropped. On the way out, `ModuleResolver` wraps the `FailedToResolve*` errors in `UnableToResolveError` (code frame, existing directories only), and `DependencyGraph` maps `DuplicateHasteCandidatesError` → `AmbiguousModuleResolutionError` and `InvalidPackageError` → `PackageResolutionError`.

Any new failure mode should carry the same kind of structured evidence. "Unable to resolve module X" with no candidate list is a support burden.

## Caching and invalidation

Three caches, deliberately different in precision, plus the hooks meant to make them precise:

### 1. `DependencyGraph._resolutionCache` — coarse

A four-level `Map` tree: `resolverOptionsKey → originDir → name + '\0esm'|'\0cjs' → platform → BundlerResolution` — the suffix because `isESMImport` picks `import` vs `require` conditions. Nested maps share prefixes rather than building one composite key, though `resolverOptionsKey` (`JSON.stringify(resolverOptions ?? {}, canonicalize)`) is recomputed per call, hits included. `canonicalize` (`metro-core/private/canonicalize`) sorts object keys so the string is stable regardless of property order.

Keyed on the **origin folder**, not the origin file — resolution depends only on the directory (plus the closest `package.json`, itself a function of the directory). The exception is a `virtualModule` result, stored under the origin *file* at the second level, in the same map as the directory keys, because a virtual path may derive from the importing file, as `metro:inline`'s does: "the same specifier in two sibling files may be two modules". A lookup tries the directory key first, then the file key. An `assumeFlatNodeModules` extra option keys a specifier with no `/` (other than `.` and `..`) from an origin outside `node_modules` on `''` instead, so one entry serves every origin; nothing in Metro passes it, and it isn't in `getGraphId` (a TODO notes this). That binds custom resolvers too: `originModulePath` "may not be the only place this dependency was found, as resolutions can be cached", and `dependency` is "provided for diagnostic purposes ONLY". **Only successes are memoized**: a throw skips the `set`, so failures re-resolve every time.

**Invalidation: the entire cache is discarded on any `'change'` event** (`_onHasteChange`), which also invalidates `PackageCache` per changed path and rebuilds the `ModuleResolver`. Haste lookups read `HastePlugin`'s live maps, so they need nothing more.

**Clearing is not re-resolving.** An entry is recomputed only when asked for again, and `DeltaCalculator` asks only for modules it revisits: modified files, inverse dependencies of deleted ones, an added file that already has a module in the graph (treated as modified), `require.context` modules whose pattern matches an added file, or everything when `#shouldReset` fires (any symlink change, or any `package.json` change under `unstable_enablePackageExports`). Other changed paths outside the graph are filtered out, so creating `Foo.ios.js` beside a resolved `Foo.js` (outside any `require.context`) changes nothing until its importer is revisited for another reason.

### 2. `PackageCache` — contents only

`packages/metro/src/node-haste/PackageCache.js` holds one map, `#packageCache`: `package.json` path → parsed contents + `rootPath`. Each file is read with `readFileSync` on first use and dropped by `invalidate(path)`, which `_onHasteChange` calls for every added, modified and removed file. It outlives `_resolutionCache` clears and graph resets.

`getPackageForModule` is **not memoized**: "The closest package is looked up on every call rather than remembered per module path. Only the parsed contents of each `package.json` are cached." Each call runs `_getClosestPackage`, a single `fileSystem.hierarchicalLookup(path, 'package.json', {breakOnSegment: 'node_modules', subpathType: 'f'})` against the live `TreeFS`, so a nearer `package.json` or a retargeted directory symlink is seen on the next lookup. A memo of the closest scope would miss exactly those two cases unless each entry recorded what it observed (`references/caching.md`, "The traps"), and the walk is cheap enough not to need one. **Don't add a scope memo without observations.**

**Known gap:** The contents map is keyed on the path it was asked for. `resolvePackageEntryPoint` asks `getPackage` with the lexical candidate path, which runs through a symlinked `node_modules/<pkg>` (workspaces, pnpm), but change events carry canonical paths, so that entry is never evicted: a package without `exports` can keep its old `main` until restart.

The `getPackageForModule` contract is specified in `metro-resolver/src/types.js`: a path through a symlinked directory checks the link's target, then continues up from the link's parent, while a symlinked file is scoped by where the link is; a missing path takes the scope of its deepest existing ancestor, or `null` if the first missing segment is `node_modules`; "The resolver calls this a few times per resolution, so it should be cheap." `getCandidatePackageScope` throws after three attempts if the returned `packageRelativePath` doesn't end in the name it asked about, so a custom context (such as Expo's) must meet the contract exactly. The member is `@deprecated` in `types.js`, yet browser-field redirection, `imports`, `exports`, self-resolution and per-directory candidate scopes all use it.

### 3. Graph-level — `getGraphId`

`packages/metro/src/lib/getGraphId.js` produces the identity of a whole graph from entry file + `customResolverOptions` + `customTransformOptions` + `dev`/`minify`/`platform`/`type`/`experimentalImportSupport`/`lazy`/`shallow`/`unstable_allowRequireContext`/`unstable_transformProfile`, via `JSON.stringify(..., canonicalize)`. `IncrementalBundler` keys live graph revisions on it.

**If you add a per-request option that changes resolution or transformation output, it must appear in `getGraphId`** — otherwise two logically different bundles share one graph revision. (`config.resolver` options needn't: config is fixed for the server's lifetime.)

### 4. Observation hooks

`fileSystemLookup` and `_getClosestPackage` could pass `TreeFS` an `Observations` record to learn what each resolution depended on (`references/file-map.md`); that is the intended foundation for per-resolution invalidation, so build there rather than on a new seam. Its status is in SKILL.md's "Unused and gated mechanisms".

## Adding a resolver feature — the checklist

1. Add the capability to `ResolutionContext` (`metro-resolver/src/types.js`), documented there and in `docs/Resolution.md`'s "Resolution context" section, and update `metro-resolver`'s API snapshot. A config-backed member also needs its `metro-config` type, default, API snapshot and `docs/Configuration.md` entry.
2. Bind it in `createModuleResolver.js`, backed by `TreeFS`/`PackageCache`, and thread it through `ModuleResolver`'s `Options` and the per-call context in `ModuleResolution.js` (where per-request values such as `isESMImport` are added).
3. Keep `resolve.js` pure and total: every branch either returns a `Resolution` or throws a typed error with candidates.
4. Decide whether it affects the resolution *result* for a given `(resolverOptions, originDir, name, isESMImport, platform)` — origin file, for a virtual result. If it does and isn't covered by that key, it belongs in `customResolverOptions` (and therefore in `getGraphId`).
5. Ask what invalidates it — and what re-runs it, since a cleared entry only helps if asked for again. If it reads a file, that file's changes must invalidate — via the blanket `_resolutionCache` clear or, for file *contents*, a cache keyed on the canonical (real) path and evicted in `_onHasteChange` — not on the path as asked (`PackageCache`'s known gap). Don't memoize a `TreeFS` answer (existence, scope) beneath the resolution cache unless each entry records its `Observations`.
6. Gate anything not yet stable behind `unstable_`, and document in `docs/Resolution.md` / `docs/Configuration.md`.
7. Test in `metro-resolver/src/__tests__` against in-memory fixtures **and** in `packages/metro/src/DeltaBundler/__tests__/resolver-test.js` (a real `DependencyGraph` over `metro-memory-fs`, posix and win32). If invalidation is involved, mutate files and resolve again — resolver unit tests can't catch a stale cache — and pass `watch: true`, because a `DependencyGraph` without it watches only when not on CI.

## Virtual resolutions (gated)

Off by default; status in SKILL.md's "Unused and gated mechanisms". A resolver can return a module with no file, `{type: 'virtualModule', virtualPath, source}` (`VirtualResolution`, `metro-resolver/src/types.js`, which states the contract): a virtual path names exactly one module, a resolver "must produce the same `source` for the same virtual path wherever it is resolved from", and imports inside it resolve from the virtual path's directory. With `resolver.unstable_allowVirtualModules`, `ModuleResolver` turns it into a `BundlerResolution` at `virtual:<virtualPath>` with the source and its sha1 (how the graph carries it: `references/graph.md`), and `_resolutionCache` stores it per origin *file* (above). Metro's own producer is `metro:inline,<percent-encoded source>` / `metro:inline;base64,…` (`lib/resolveInlineModule.js`), which names the module beside its importer after a hash of its source, so it is a pure function of (origin, specifier) and can't go stale. A resolver returning virtual modules is held to the same purity rule as `resolve.js`.
